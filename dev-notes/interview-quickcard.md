## 六大王牌（每个按"一句表述 → 关键数字 → 追问三层"准备）

### ① 点赞幂等 + InnoDB 死锁
- **一句**：点赞从"先查后写"竞态（同用户并发 10 请求全部成功、计数+10）改造为 ZADD 原子占位
  + 复合主键明细表事实源，过程中真实撞上并解决了 MySQL 死锁。
- **数字**：并发超发 +10→零超发；liked==明细行数对账一致；写路径 QPS 465→1005；P99 375→114ms。
- **追问层**：
  1. 竞态根因：ZSCORE 查重和 ZADD 写入两步之间无原子性 → 改用 ZADD 返回值单命令原子判断。
  2. 死锁成因：同用户并发 toggle 时，事务 A 持明细行锁等计数行锁、事务 B 反之，锁环；
     MySQL 检测后回滚 victim → TransactionTemplate 收紧事务 + 线性退避重试（重试体因
     INSERT IGNORE/affected 判断天然幂等）。
  3. 取舍：宁可 500 拒绝绝不超发（fail-safe）；双写一致性以 DB 明细为准，Redis 丢数据时
     affected=0 惰性自愈，无需重建任务。

### ② MQ 可靠消息闭环（故障演练先行）
- **一句**：先用故障演练复现三类真实缺陷再修复——毒消息 15 秒 40.8 万行日志无限循环、
  broker 宕机发帖 500 但帖子已入库、重复消息双重消费——四件套全部收敛。
- **数字**：毒消息日志 408,723→138 行（-99.97%）；宕机发帖 500→200+45 秒内自动补偿重投。
- **追问层**：
  1. 毒消息根因：容器默认 requeue=true，消费异常→重新入队→死循环；改本地重试 3 次
     （1s/2s/4s）+ 耗尽 reject 进死信队列（DLX），死信消费者告警+Redis 计数。
  2. 补偿设计：afterCommit 投递失败 catch 住（不再让接口 500——事务已提交、帖子已入库，
     500 会让用户重发造成不一致），消息落 Redis 补偿队列，@Scheduled 20s 重投至恢复。
  3. 局限（主动交代）：补偿队列本身在 Redis，Redis+Rabbit 同时挂会丢，完整方案是本地
     消息表/事务消息——能说出局限反而加分。

### ③ 中文搜索 FULLTEXT ngram
- **一句**：前置模糊 LIKE（索引失效全表扫 10,019 行）改 ngram 全文索引 + BOOLEAN MODE
  短语匹配，与 LIKE 子串语义精确等价（5 组关键词命中数全等）且免疫操作符注入。
- **数字**：单次延迟 -31%~-71%；并发 QPS 342→926（2.7x）；P99 529→127ms。
- **追问层**：
  1. ngram 原理：中文无天然分词，ngram parser 按 2 字符切二元组建倒排；查询词同样切分后匹配。
  2. 等价性关键：双引号包裹查询词变成短语匹配——要求 bigram 序列相邻，恰好等价子串语义；
     服务层剥离用户输入的双引号防语法注入；单字（低于 ngram_token_size）自动回退 LIKE。
  3. 为什么不用 ES：数据量 1 万、已有 MySQL，引入 ES 是新组件运维成本；判据是数据量
     上千万或需要分词/拼音/相关度排序时再上。

### ④ 零停机安全演进（BCrypt 迁移 + 密钥轮换）
- **一句**：admin 密码 MD5→BCrypt 用"登录时识别存量格式、校验通过即原位升级哈希"实现
  零停机迁移；JWT 密钥轮换用 legacy 密钥列表让旧 token 验签回退，全程在线用户零掉线。
- **数字**：实测存量账号登录后 DB 密码当场变 $2a$10$；换新密钥后旧 token 200、伪造 token 401。
- **追问层**：
  1. 为什么不批量重置：发公告强制改密伤体验且集中风险；逐账号下次登录时切换，用户无感。
  2. 轮换流程：换新主密钥重启 → 旧 token 靠 legacy 列表继续验签（TTL 内自然过期）→ 清空
     legacy 完成轮换；admin/user 独立 legacy 保持双密钥角色隔离。
  3. 代价认知：BCrypt 校验慢 ~100ms（自适应哈希成本换安全，值得）。

### ⑤ 可观测性（traceId + 大盘）
- **一句**：网关生成 X-Trace-Id → 服务 MDC → MQ 消息头 → 消费者回填，实测同一 traceId
  贯穿发帖请求的 HTTP 线程与 MQ 消费线程日志；Prometheus+Grafana 大盘全自动 provisioning。
- **数字**：服务端 P95 3ms vs 客户端 106ms @c=50（口径差=并发排队，"慢在哪一层"的证据）。
- **追问层**：
  1. 网关为什么不用 MDC：WebFlux 反应式线程切换，ThreadLocal 不可靠——网关只负责生成
     与透传，日志落地在服务端。
  2. 踩坑：Micrometer 默认不发 http_server_requests 直方图分桶，不开
     percentiles-histogram 则 histogram_quantile 查不了 P95/P99。
  3. 用法举例：压测时连接池 active=0/pending=0 证明缓存命中路径 DB 零压力。

### ⑥ 多级缓存架构深度治理（Caffeine + Redis + 布隆过滤器 + Pub/Sub 广播）
- **一句**：从单层 Redis 演进为 L1 Caffeine 本地毫秒读 + L2 Redis 逻辑过期防击穿 + Redisson 分布式布隆过滤器 0.1ms 防穿透，配合 Redis Pub/Sub 广播实现跨节点本地缓存协同失效，读热点 QPS 破万。
- **数字**：热点诗词吞吐量从单 Redis 977 QPS 跃升至 11,200+ QPS (11.5x)；P99 延迟 114ms 下降至 3.2ms；非法大整数恶意扫号布隆过滤器拦截率 100%，DB 与 Redis 穿透压力降为 0。
- **追问层**：
  1. 为什么上 Caffeine 多级缓存：单层 Redis 哪怕内网往返也有 1~3ms 网络 I/O 与序列化开销，连接数与网卡带宽是吞吐瓶颈；Caffeine 直接读 JVM 堆内内存（~0.05ms），将单机热点吞吐推高一个数量级。
  2. 多实例本地缓存一致性怎么做：采用 Cache-Aside 写路径（先更 DB，再删 Redis，最后发送 Redis Pub/Sub 广播 `cache:evict:topic`）；集群中所有微服务节点挂载 `MessageListener`，监听到广播后协同执行 `caffeine.invalidate(id)`，实现微秒级本地缓存失效。
  3. 布隆过滤器误判率与动态预热：选用 Redisson `RBloomFilter`（预设 10 万容量，1% 容错率，底层位图由 Redis 统一维护，集群共享）；应用启动时由 `ApplicationRunner` 后台异步全量加载已存在 ID，新增记录时双写注入；管理端暴露 `/admin/cache/warmup` 与 `/admin/cache/stats` 供运维演练与指标大盘实时观测。

## 取舍题防线（"为什么不用 X"系列，一句答法）

- **多级缓存演进决策（Caffeine + 布隆过滤器）**：早期单机阶段单 Redis 足够；当集群多实例部署且读接口面临万级高并发（如热门诗词榜单/开屏推荐）时，单层 Redis 的网络 I/O 成为性能天花板，因而演进为 Caffeine + Redis 两级缓存，并用布隆过滤器封死非法 ID 的穿透攻击，用 Pub/Sub 解决跨节点失效问题。
- **为什么不用ES**：1万数据 FULLTEXT ngram 够用；判据=千万级/需分词拼音相关度。
- **为什么补偿不用本地消息表**：轻量补偿够当前规模，本地消息表是 Redis+MQ 同时挂的
  完整方案（主动说局限）。
- **为什么项目用 jar 不用 IDE 直跑**：多模块改 pojo 要 -am 联编否则用过期构件；压测需要固定产物。
