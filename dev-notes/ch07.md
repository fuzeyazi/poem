## 阶段 1:brainstorm 定稿(2026-10-22)

**用户关键原话(需求要点):**
- "我要用 **Superpowers 模式**把客服系统的工具层从几个写死的内置工具,升级成**即插即用的工具系统**。"
- 需求 1:"不管内置还是 MCP 来的工具,一律带齐工具名、用途描述、JSON Schema 参数定义三样,登记进同一份工具表;内置工具服务启动时登记,MCP 工具连上 Server **动态发现、现问现拿**;新工具注册进来就能被主力 Agent 用上,**不改核心代码、不重启服务**。"
- 需求 2:"工具执行前统一按 JSON Schema 校验一遍……拦下不抛异常了事,把校验错误说明包成一条工具结果回灌给模型。"
- 需求 3:"工具分只读、写两类,写操作由执行引擎把门;本系统的写操作就 create_ticket 一个……真正执行还要等第 7 点的前端确认回来,没确认的调用引擎直接拒绝……外部 MCP 工具的用途声明是对方自己写的、不可信,能不能调只认我们这侧的权限规则。"
- 需求 4:"所有工具调用走同一处,统一管超时、重试、错误处理、结果格式化;重试只给网络抖动……业务空结果不重试,写操作默认不自动重试……错误按参数不合法、查询落空、真故障三类分诊……内部枚举码翻成人话、序列化 JSON 中文不转义。"
- 需求 5:"建 tool_audit_logs 表,每次工具调用落一条……被权限拒、被校验拦的调用同样要落;审计表不挂外键,写审计失败不许反过来拦工具执行。"
- 需求 6:"自建两个业务 MCP Server——物流、售后,各自独立进程……客服系统作为 MCP Client 接入,拿回的工具跟内置清单合成一份,主力 Agent 一视同仁地调;物流查询由物流 MCP Server 接管,第 2 章内置的 query_logistics 从清单里下线,别留重名工具。"
- 需求 7:"客户明确要求建工单才走这条流,Agent 先核对信息够不够……凑齐后发起 create_ticket,执行引擎不直接执行,照第 6 章订单选择器的做法用 **LangGraph interrupt** 把工单预览推给前端……点确认,回传后端 resume 放行,落 tickets 表,回复里把工单号带给用户;点取消,不执行,这次调用按「权限拒绝」落审计;第 5 章投诉流程里前端按钮建单那条路保持不动。"
